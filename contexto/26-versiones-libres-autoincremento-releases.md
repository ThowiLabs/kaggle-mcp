# Versiones libres y autoincremento para GitHub Releases (2026-10-11)

Corrección de `.github/workflows/release.yml`: previamente `workflow_dispatch` exigía `vMAJOR.MINOR.PATCH` y el usuario obtuvo error al introducir `1.0`. Ahora `inputs.version` es opcional. Si está vacío, el job `build` lee tags Git remotos disponibles tras `actions/checkout@v4` con `fetch-depth: 0` y obtiene el mayor `MAJOR.MINOR` o `vMAJOR.MINOR`, incrementando el segundo campo; si no existe ninguno, asigna `1.0`. Ejemplos: 1.0 -> 1.1 -> 1.2 -> 1.10 (después de 1.9); 2.5 -> 2.6. Las versiones manuales personalizadas (`1.0`, `3.5`, `beta-1`, `v1.2.3`) se usan tal cual, siempre que sean tags Git seguros y no contengan espacios ni caracteres de shell peligrosos.

La selección vive en `scripts/release_version.py`. El tag resuelto se distribuye mediante `GITHUB_ENV`, `GITHUB_OUTPUT` y `needs.build.outputs.tag` a compilación y publicación, manteniendo archivos, binarios, nombre de Release y tag consistentes. Se admite disparar en push de tags `v*` y `[0-9]*`. Grupo concurrency serializado por repositorio, `cancel-in-progress:false`. Un tag existente no se reescribe y una Release existente se rechaza. `scripts/test_release_version.py` valida casos numéricos, personalizados, rechazo de nombres inválidos y un repositorio Git temporal real.

Verificaciones locales: 9 tests unitarios en Python (incluyendo integración Git), actionlint, notebook simulado, Go tests y go vet; todas pasaron. No se creó etiqueta remota ni se publicó una Release; es necesario subir el commit para que GitHub Actions use esta corrección.
